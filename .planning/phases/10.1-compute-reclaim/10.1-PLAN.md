<threat_model>
  <assets>
    <asset>User compute balances for both original giver and receiver.</asset>
    <asset>Transaction logs used as the source of reclaimable amount and user-visible audit trail.</asset>
    <asset>Authentication context identifying the original giver.</asset>
    <asset>APP query and reclaim submit payloads.</asset>
  </assets>
  <risks>
    <risk>A user could attempt to reclaim compute they did not originally gift.</risk>
    <risk>Receiver may consume compute between query and submit, causing stale reclaimable amount.</risk>
    <risk>Partial reclaim may be repeated unless previous reclaim amount is associated with the source gift.</risk>
    <risk>Concurrent reclaim taps could double-deduct receiver balance.</risk>
    <risk>Freeform transaction log remarks could be misused as the only business discriminator.</risk>
  </risks>
  <mitigations>
    <mitigation>Scope source gift lookup by current authenticated user id, target phone, active rows, type `OUT`, and original gift marker.</mitigation>
    <mitigation>Recalculate latest gift, receiver consumption, already reclaimed amount, and receiver current balance inside the reclaim transaction.</mitigation>
    <mitigation>Add `related_log_id` or equivalent source-log linkage to reclaim logs and subtract already reclaimed amount.</mitigation>
    <mitigation>Lock both users with pessimistic write locks before balance mutation.</mitigation>
    <mitigation>Return the exact stale message when backend recalculation rejects the requested amount.</mitigation>
  </mitigations>
</threat_model>

  <action>
    Add `GET /compute/reclaim/latest?toPhone=...` and `POST /compute/reclaim` under the existing compute controller.

    Implement one shared `calculateReclaimable(...)`/equivalent service method that resolves the receiver, latest source gift, receiver consumed amount, already reclaimed amount, and reclaimable amount. Both endpoints must call this method.

    Query endpoint:
    - require login;
    - validate phone;
    - find latest original gift from current user to the phone;
    - if absent, return `未查询到您给对方的赠送记录`;
    - return gift log id, target phone/name, gift amount, gift time, receiver consumed amount, already reclaimed amount, and reclaimable amount.

    Submit endpoint:
    - require login;
    - validate positive amount;
    - lock current user and receiver;
    - call the same shared reclaimable calculation method inside the transaction after locks are acquired;
    - reject stale/over-limit requests with `对方新增了消耗，请重新查询可取回算力`;
    - deduct receiver balance and credit current user balance;
    - normalize receiver non-transferable balance;
    - save paired logs:
      - current user `IN`, `remark = 从{receiverPhone}取回`, `related_log_id = sourceGiftLog.id`;
      - receiver `OUT`, `remark = 赠送方{currentUserPhone}取回`, `related_log_id = sourceGiftLog.id`;
    - return updated balances and reclaim summary.
  </action>

    - Successful reclaim updates both user balances and writes both user-visible logs.
    - There is only one implementation of可取回数量计算 in `ComputeService`.
