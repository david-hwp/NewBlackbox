# Phase 10.1: 算力取回 - Context

## User Request

在 APP 侧新增一个“算力取回”功能：

- 入口放在“我的 -> 算力赠送”的下面。
- 用户点击后进入新页面。
- 页面显示“对方手机号”的 label 和输入框，输入框旁边加查询按钮。
- 点击查询后，服务器按当前登录用户和接收方手机号查询最新一条赠送交易日志。
- 后端再查询这条交易日志之后接收方发生的总消耗数，计算可取回数量，并把可取回数量拼到交易日志查询结果中返回给 APP。
- APP 用小票式卡片展示：
  - 对方手机号
  - 交易发生时间
  - 用户消耗算力
  - 可取回算力：转赠总数 - 接收方消耗
- 页面底部有取回按钮。
- 用户点击取回后弹窗输入取回算力个数，默认值是可取回数量。
- APP 校验字段类型和数量；如果输入大于可取回数量，在输入框下方红字提示：`不得超过可取回算力个数`。
- 后端收到取回请求后，必须重新查询数据库计算可取回数量，校验通过后才执行取回。
- 查询接口计算可取回算力和取回接口二次校验可取回算力必须复用同一个后端计算方法，不能复制两套逻辑。
- 如果没有查询到赠送记录，提示：`未查询到您给对方的赠送记录`。
- 如果后端二次校验失败，提示：`对方新增了消耗，请重新查询可取回算力`。
- 取回成功后记录两条交易日志：
  - 接收方日志：`赠送方xxx取回`
  - 当前用户日志：`从yyy取回`

## Current Implementation Summary

### Backend

- 算力赠送入口是 `POST /api/compute/gift`，实现位于 `GiftController.gift()` 和 `ComputeService.giftCompute()`。
- 当前登录用户从 `AuthContext.getUserId()` 获取。
- 用户余额字段：
  - `users.compute_balance`：总算力余额。
  - `users.non_transferable_compute_balance`：不可转赠算力余额。
- 赠送时只允许赠送可转赠余额：`compute_balance - non_transferable_compute_balance`。
- 赠送成功后写两条 `transaction_logs`：
  - 赠送方：`type = OUT`，`to_phone`，`to_name`，`remark = 赠送算力给 {toPhone}`。
  - 接收方：`type = IN`，`from_phone`，`from_name`，`remark = 收到 {fromPhone} 赠送的算力`。
- 店铺创建/续期扣费写 `type = CONSUME`，并会优先减少 `non_transferable_compute_balance`。
- 交易日志当前只有 `type`，没有业务子类型或关联源日志字段。
- `TransactionLogRepository` 已有按用户、类型、时间区间分页查询，但没有“最新赠送记录”“某日志之后消耗汇总”“已取回汇总”等专用查询。

### Android APP

- “我的”页面是 `ProfileActivity` + `activity_profile.xml`。
- “算力管理”区块已有 `menuGift` 和 `menuLogs`。
- “算力赠送”页面是 `GiftActivity` + `GiftViewModel` + `ComputeRepository`。
- `ApiService` 已定义 `giftCompute()` 和 `getMyLogs()`。
- 交易日志页对 `IN/OUT/CONSUME` 做列表展示；`IN` 类型如果 `remark` 有值，会直接显示 remark。
- 当前没有“算力取回”页面、DTO 或 API。

## Phase Boundary

### In Scope

- 后端新增算力取回查询接口。
- 后端新增算力取回执行接口。
- 后端新增必要的交易日志关联字段或等价机制，确保部分取回、多次查询和重复提交不会超取。
- APP “我的”页新增“算力取回”入口，位置在“算力赠送”下方。
- APP 新增算力取回页面、ViewModel、Repository DTO 和 Retrofit API。
- APP 页面以小票式卡片展示查询结果。
- APP 取回弹窗默认填充可取回数量，并做数量/类型校验。
- 后端事务内锁定双方用户，重新计算可取回数量，防止查询后对方新增消耗或重复提交导致余额错误。
- 交易日志列表不新增筛选按钮；只要求新取回日志按现有 `IN/OUT` 展示，并显示对应 remark。

### Out of Scope

- 不改 Phase 11 渠道体系。
- 不改不可转赠算力的定义和扣费优先级。
- 不做管理后台页面。
- 不支持取回非当前登录用户赠送的算力。
- 不支持指定历史赠送记录列表；本阶段只取“给该手机号的最新一条赠送记录”。
- 不新增交易日志筛选按钮。
- 不改变店铺创建/续期扣费逻辑。

## Locked Decisions

- “算力取回”的发起人是当前登录用户，并且必须是原始赠送方。
- 查询条件是当前登录用户的最新 `OUT` 赠送日志，接收方手机号等于用户输入手机号。
- 为避免把取回日志误判为赠送日志，最新赠送日志查询必须限定为原始赠送行为，例如 `type = OUT`、`to_phone = targetPhone`、`remark` 符合当前赠送日志格式，或使用后续新增的业务子类型/关联字段。
- 可取回数量允许等于可取回上限；校验规则是 `amount <= reclaimableAmount`，不是严格小于。
- 需要考虑已部分取回的场景；实际可取回数量应扣除已经针对同一赠送日志取回过的数量，避免重复取回超过原始赠送数量。
- 推荐新增 `transaction_logs.related_log_id` 或等价字段，把取回日志关联到原始赠送日志。
- 查询无赠送记录返回业务错误：`未查询到您给对方的赠送记录`。
- 执行取回时，后端必须重新查询最新赠送日志、消耗量、已取回量和双方当前余额。
- 查询接口和取回接口必须共用同一个 `calculateReclaimable(...)`/等价私有服务方法，确保赠送日志选择、接收方消耗汇总、已取回汇总、可取回数量计算口径完全一致。
- 如果后端重算后请求金额大于可取回数量，返回：`对方新增了消耗，请重新查询可取回算力`。
- 取回成功时扣减接收方 `compute_balance`，增加当前用户 `compute_balance`。
- 取回不改变当前用户的 `non_transferable_compute_balance`；接收方被扣减时 `non_transferable_compute_balance` 需要归一化为不大于扣减后的总余额。
- 取回成功写两条日志：
  - 当前用户：`type = IN`，`amount = 取回数量`，`from_phone = 对方手机号`，`remark = 从{对方手机号}取回`。
  - 对方用户：`type = OUT`，`amount = 取回数量`，`to_phone = 当前用户手机号`，`remark = 赠送方{当前用户手机号}取回`。

## Risks

- 如果不记录源赠送日志和已取回量，部分取回后可能重复取回，造成余额超发。
- 如果查询接口和取回接口各自实现一套可取回计算逻辑，后续维护时容易出现展示值和实际校验值不一致，这是 P0 风险。
- 如果只按手机号查日志，不校验当前登录用户是原始赠送方，可能越权取回别人的赠送。
- 查询后到提交取回之间，接收方可能新增消耗；必须后端二次校验。
- 并发点击取回按钮可能导致重复扣款；需要事务和用户行锁。
- 接收方余额可能因为其他操作低于理论可取回数量；执行取回前还要校验接收方当前余额足够。
- 交易日志 remark 是用户可见文案，不能作为唯一安全边界；如果暂时复用 remark，必须同时用用户、手机号、类型、时间和关联字段做约束。

## Acceptance Criteria

- “我的 -> 算力管理”中，“算力赠送”下方出现“算力取回”入口。
- 算力取回页面能输入对方手机号并查询。
- 无赠送记录时，APP 展示 `未查询到您给对方的赠送记录`。
- 查询成功后，APP 用小票式卡片展示对方手机号、交易发生时间、用户消耗算力、可取回算力。
- 取回弹窗默认填入可取回数量。
- APP 输入非正整数或大于可取回数量时不发请求；大于可取回数量时显示 `不得超过可取回算力个数`。
- 后端执行取回时重新计算可取回数量；如发生变化导致请求超额，返回 `对方新增了消耗，请重新查询可取回算力`。
- 查询接口和取回接口的可取回数量来自同一个后端计算方法；代码审查时不能存在两套重复计算实现。
- 取回成功后，接收方余额减少，当前用户余额增加。
- 取回成功后双方交易日志各新增一条，并可在现有 APP 交易日志列表中显示对应 remark。
- 部分取回后再次查询，可取回数量会减少，不能重复取回超过原始赠送剩余额度。
- 后端单元测试覆盖：无赠送记录、可取回计算、部分取回、重复取回拦截、接收方新增消耗导致校验失败、并发/行锁关键路径。
