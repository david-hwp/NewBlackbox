# Phase 10.1 Research: 算力取回

## Existing Code Paths

### Gift Flow

- `GiftController` exposes `POST /compute/gift`.
- `ComputeService.giftCompute(fromUserId, toPhone, amount)`:
  - validates positive amount;
  - loads sender by id;
  - calculates transferable balance as `compute_balance - non_transferable_compute_balance`;
  - rejects if transferable balance is insufficient;
  - loads receiver by phone;
  - deducts sender `compute_balance`;
  - credits receiver `compute_balance`;
  - writes sender `OUT` transaction log;
  - writes receiver `IN` transaction log.

Current gift log shape is sufficient to find a sender's latest gift to a phone, but not sufficient to robustly track partial reclaims unless a new relation/subtype is introduced.

### Consumption Flow

- `ComputeService.deductCompute()` and clone create/renew deduction write `type = CONSUME`.
- Deduction reduces `non_transferable_compute_balance` first when it is positive.
- Reclaim calculation should use receiver `CONSUME` logs after the source gift log. This follows the user's requested formula.

### Transaction Log Model

Current `transaction_logs` fields:

- `id`
- `user_id`
- `type`
- `amount`
- `platform`
- `shop_name`
- `from_phone`
- `from_name`
- `to_phone`
- `to_name`
- `remark`
- `deleted`
- `created_at`

Recommended extension for reclaim correctness:

- `related_log_id BIGINT NULL` referencing the source gift transaction log.

Reason:

- Without a relation to the source gift, a partial reclaim can be repeated because the source gift amount and receiver consumption do not change.
- A nullable field is backward-compatible for all existing logs.
- Reclaim logs can be summed by `related_log_id` to calculate already reclaimed amount.

### APP Navigation And UI

- `ProfileActivity` handles “我的” page menu clicks.
- `activity_profile.xml` already has a “算力管理” section with:
  - `menuGift`
  - `menuLogs`
- `GiftActivity` is a useful reference for toolbar, account card, input validation, ViewModel, and `ComputeRepository`.
- Existing design uses full-width white cards, 8dp-ish corners via `bg_card_white`, restrained green accents, and bottom fixed action bars.

## Proposed Backend API

## Shared Calculation Contract

Query and submit must share one service-level calculation method. Suggested shape:

```java
private ReclaimComputation calculateReclaimable(Long fromUserId, String toPhone)
```

or:

```java
private ReclaimComputation calculateReclaimable(User fromUser, User toUser)
```

This method owns all of the following logic:

- resolving receiver by phone;
- selecting the latest original gift log;
- summing receiver consumption after the source gift;
- summing already reclaimed amount for the source gift;
- calculating `reclaimableAmount`;
- returning the source gift log, receiver user, consumed amount, reclaimed amount, and reclaimable amount.

The query endpoint should convert this method result into a response DTO.

The submit endpoint should call the same method inside its transaction after locking both users, then only add validation and mutation. Do not copy the SQL or arithmetic in the submit path.

Acceptance rule: if a future change modifies可取回数量口径, it should require editing one method only.

### Query Latest Reclaimable Gift

`GET /api/compute/reclaim/latest?toPhone={phone}`

Auth:

- Requires login.
- `fromUserId = AuthContext.getUserId()`.

Behavior:

1. Validate phone format or at least non-empty phone.
2. Resolve receiver user by phone.
3. Find latest source gift log:
   - `user_id = fromUserId`
   - `type = OUT`
   - `to_phone = toPhone`
   - `deleted = 0`
   - original gift behavior only, not reclaim logs
   - order by `created_at desc, id desc`
4. If none found, return error message `未查询到您给对方的赠送记录`.
5. Sum receiver consumption after the source gift:
   - `user_id = receiver.id`
   - `type = CONSUME`
   - `created_at/id` after source log
   - `deleted = 0`
6. Sum already reclaimed amount for the source gift:
   - `related_log_id = sourceGiftLog.id`
   - current user's reclaim `IN` logs or both paired logs, but count only one side to avoid double counting.
7. `reclaimableAmount = max(0, sourceGiftLog.amount - consumedAmount - reclaimedAmount)`.
8. Return source gift details plus computed amounts.

Suggested response:

```json
{
  "giftLogId": 123,
  "toPhone": "13800138000",
  "toName": "张三",
  "giftAmount": 10,
  "giftCreatedAt": "2026-06-10T12:00:00",
  "receiverConsumedAmount": 3,
  "alreadyReclaimedAmount": 2,
  "reclaimableAmount": 5
}
```

The APP only needs to display the required fields. `alreadyReclaimedAmount` is useful for debugging and future UI but does not need to be emphasized if the current UI should stay compact.

### Execute Reclaim

`POST /api/compute/reclaim`

Request:

```json
{
  "toPhone": "13800138000",
  "giftLogId": 123,
  "amount": 5
}
```

Behavior:

1. Requires login.
2. Validate positive integer amount.
3. Start transaction.
4. Lock current user and receiver rows with pessimistic write locks.
5. Re-run the same latest-gift lookup and computed reclaimable calculation.
6. If no source gift, return `未查询到您给对方的赠送记录`.
7. If request `giftLogId` is present and no longer equals latest gift log id, return `对方新增了消耗，请重新查询可取回算力`.
8. If `amount > reclaimableAmount`, return `对方新增了消耗，请重新查询可取回算力`.
9. If receiver current balance is less than amount, return the same stale message.
10. Deduct receiver balance by amount.
11. Credit current user balance by amount.
12. Normalize receiver non-transferable balance to not exceed receiver total balance.
13. Save two related transaction logs:
    - current user: `IN`, `from_phone = receiver.phone`, `remark = 从{receiverPhone}取回`, `related_log_id = giftLogId`.
    - receiver: `OUT`, `to_phone = currentUser.phone`, `remark = 赠送方{currentUserPhone}取回`, `related_log_id = giftLogId`.
14. Return updated balances and reclaim summary.

## Query Details

Use timestamp plus id for stable “after gift” semantics:

- A log is after source gift if:
  - `created_at > source.created_at`, or
  - `created_at = source.created_at and id > source.id`.

This avoids edge cases when two logs share the same second.

Latest source gift query should not match reclaim logs. Strongest option:

- Add a new nullable `business_type` later, but for this phase `related_log_id` plus existing remark convention is enough:
  - original gift `OUT` logs have `remark like '赠送算力给 %'`;
  - reclaim `OUT` logs have `remark like '赠送方%取回'` and a non-null `related_log_id`.

## Testing Strategy

Backend tests:

- Query no receiver/no gift returns `未查询到您给对方的赠送记录`.
- Query latest gift ignores older gifts to same phone.
- Query subtracts receiver consumption after source gift.
- Query subtracts already reclaimed amount.
- Reclaim with amount equal to reclaimable succeeds.
- Reclaim with amount greater than reclaimable returns `对方新增了消耗，请重新查询可取回算力`.
- Reclaim after receiver new consume between query and submit fails with stale message.
- Partial reclaim then second query returns reduced reclaimable amount.
- Logs are written with exact user-visible remarks.
- Receiver non-transferable balance is normalized after deduction.

APP verification:

- `./gradlew :app:assembleDebug`
- Navigate: 我的 -> 算力取回.
- Invalid phone shows phone error.
- No record shows server message.
- Query success renders receipt card.
- Amount dialog default equals可取回数量.
- Amount larger than可取回数量 shows exact red error and does not call backend.
- Successful reclaim updates current balance and the existing transaction log page shows `从yyy取回` / `赠送方xxx取回` remarks.
