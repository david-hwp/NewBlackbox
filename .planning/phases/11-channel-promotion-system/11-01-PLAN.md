<threat_model>
  <assets>
    <asset>Existing production users, shops, compute balances, transaction logs, feedback, announcements, app versions, and engine versions.</asset>
    <asset>Channel tenant boundary and role authorization decisions.</asset>
    <asset>CHANNEL admin compute balance, which becomes that channel's distributable pool.</asset>
    <asset>APP request channel header `X-Apk-Channel` and old APK fallback behavior.</asset>
  </assets>
  <risks>
    <risk>Migration could orphan or hide existing rows if channel backfill is incomplete.</risk>
    <risk>Channel admin could read or mutate another channel if filters are applied inconsistently.</risk>
    <risk>Phone uniqueness migration could block production startup or merge unrelated users.</risk>
    <risk>Disabled-channel handling could leak partial functionality if only implemented in some controllers.</risk>
    <risk>Client-supplied channel values could be used to spoof cross-channel access without server-side trust boundaries.</risk>
  </risks>
  <mitigations>
    <mitigation>Backfill every legacy row to the seeded `main` channel before enforcing non-null constraints where safe.</mitigation>
    <mitigation>Centralize role and channel checks in `PermissionService` and `ChannelScopeService` instead of per-controller ad hoc logic.</mitigation>
    <mitigation>Keep admin login phone uniqueness in service validation and migrate normal-user uniqueness to active `(channel_id, phone)`.</mitigation>
    <mitigation>Resolve APP request channel from `X-Apk-Channel`, fallback to legacy field/main, then enforce active-channel status once.</mitigation>
    <mitigation>Do not trust request parameters for CHANNEL admin scope; derive scope from authenticated principal.</mitigation>
  </mitigations>
</threat_model>
